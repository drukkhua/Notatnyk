# План: калькулятор величин для Notatnyk и поля ТЗ BitrixUI

Дата: 05.09.2026

## 1. Цель

Добавить в общий синтаксис ТЗ вычисления с произвольными единицами измерения:

```text
Итого: 3720 грн - 10% =  →  Итого: 3 348,00 грн
50 шт + 50 шт =          →  100 шт
100 м2 - 25 м2 =         →  75 м2
5 автомобилей - 10% =    →  4,5 автомобилей
50 шт * 2 =               →  100 шт
100 шт / 4 =              →  25 шт
```

Единица должна быть произвольным пользовательским текстом, а не значением из закрытого справочника. Движок не обязан понимать физический смысл `шт`, `м2` или `автомобилей`; он должен безопасно переносить единицу результата и проверять совместимость операций.

Изменение необходимо реализовать одинаково в:

- Notatnyk: `src/parser.js`;
- BitrixUI: `frontend/src/lib/specEngine.ts`;
- рабочем просмотре, клиентском режиме и построчном редакторе;
- общих contract-fixtures обоих проектов.

## 2. Причина текущей ошибки

Функция `calc()` уже правильно вычисляет:

```text
3720 - 10% = 3348
```

Ошибка возникает в `inline()` из-за порядка замен:

1. `RE.price` раньше калькулятора превращает `3720 грн` в HTML цены.
2. `RE.calc` больше не видит базовое число и единицу.
3. Из оставшегося текста распознаётся только `10% =`.
4. Одиночный процент вычисляется как `0,1`.

Для `50 м2 + 10% =` ситуация ещё хуже: старый числовой шаблон может принять цифру `2` из единицы `м2` за начало формулы.

Следовательно, исправлять только регулярку `RE.calc` нельзя. Выражение с единицами необходимо извлекать из исходного текста до денежного рендера и до генерации HTML.

## 3. Объём первой версии

### Поддерживаемые значения

```ts
type CalcValue =
  | { kind: "scalar"; value: number }
  | { kind: "percent"; value: number }
  | { kind: "quantity"; value: number; unitRaw: string; unitKey: string }
```

- `scalar` — обычное число без единицы;
- `percent` — число с суффиксом `%`;
- `quantity` — число или числовая переменная с произвольной единицей.

Числовую переменную следует поддержать сразу:

```text
[тираж] шт + 50 шт =
[цена] грн - 10% =
```

Строковые переменные в вычисления не допускаются.

### Поддерживаемые операции

| Выражение | Результат | Правило |
|---|---|---|
| `quantity + quantity` | `quantity` | Только одинаковые `unitKey` |
| `quantity - quantity` | `quantity` | Только одинаковые `unitKey` |
| `quantity + percent` | `quantity` | Процент от текущего левого значения |
| `quantity - percent` | `quantity` | Процент от текущего левого значения |
| `quantity * scalar` | `quantity` | Единица сохраняется |
| `scalar * quantity` | `quantity` | Единица сохраняется |
| `quantity / scalar` | `quantity` | Делитель не равен нулю |
| `quantity * percent` | `quantity` | Процент трактуется как доля |
| `scalar ± scalar` | `scalar` | Старое числовое поведение |

Не поддерживать в первой версии:

- сложение величины и числа без единицы: `50 шт + 2`;
- величины с разными единицами: `50 шт + 2 кг`;
- автоматическую конвертацию: `1 м + 50 см`;
- умножение двух величин: `2 м * 3 м`;
- деление величины на величину;
- автоматическое склонение: `1 автомобиль` / `5 автомобилей`;
- создание производных единиц вроде `м²`, `м/с` из математического смысла операции.

При неподдерживаемой операции движок не должен угадывать результат. Исходный текст остаётся неизменным, а автор получает короткую диагностику.

## 4. Однозначная грамматика

Предлагаемая логическая грамматика:

```text
expression  := sum
sum         := product ((" + " | " - ") product)*
product     := postfix ((" * " | " / ") postfix)*
postfix     := primary "%"?
primary     := number unit? | variable unit? | "(" expression ")"
variable    := "[" name "]"
```

Для выражения, содержащего единицу, бинарные операторы должны быть окружены пробелами:

```text
50 шт + 50 шт =       корректно
50 шт+50 шт =         не распознаётся как typed-выражение
100 A3+ - 10% =       единица `A3+`, оператор ` - `
10 грн/шт - 10% =     единица `грн/шт`
```

Это позволяет единице содержать цифры, дефисы, `/`, `.`, `²`, `+` и несколько слов без большого справочника и угадывания.

Старые безразмерные формулы сохраняют свободную запись без пробелов:

```text
2*3=
100-10%=
(2+3)*4=
```

### Числа

Поддержать:

```text
10
10,5
10.5
1 250
1 250,75
```

Числовой lexer должен отличать пробел-разделитель тысяч от пробела перед единицей. Предпочтительный шаблон числа:

```regex
\d+(?:[ \u00A0]\d{3})*(?:[.,]\d+)?
```

Нельзя просто удалить все пробелы из произвольного фрагмента: так легко склеить число и соседний текст.

### Единица

`unitRaw` сохраняется ровно в написанном виде и используется для вывода. `unitKey` нужен только для сравнений:

```ts
unitKey = unitRaw
  .normalize("NFKC")
  .replace(/\u00a0/g, " ")
  .replace(/\s+/g, " ")
  .trim()
  .toLocaleLowerCase()
```

Не следует автоматически считать `м2` равным `м²`, `шт` равным `штуки` или `грн` равным `UAH`. Такие алиасы можно добавить позже отдельной явной таблицей.

Ограничения единицы:

- не содержит перевод строки, `=` и управляющие символы;
- длина после `trim()` — от 1 до 64 символов;
- перед вставкой в HTML всегда проходит обычное текстовое экранирование;
- в результате сохраняется `unitRaw` первого операнда.

## 5. Семантика процентов и округления

Процент справа от `+` или `-` вычисляется от текущего накопленного значения:

```text
100 шт - 10% =       90 шт
100 шт - 10% + 20% = 108 шт
```

Вторая операция берёт 20% от 90, а не от исходных 100. Это соответствует текущей семантике `calc()` и должно быть зафиксировано тестом и документацией.

Округлять следует только конечный результат выражения:

- configured currency (`LOCALE.currency`) — ровно 2 десятичных знака;
- остальные единицы — максимум 6 знаков после запятой без завершающих нулей;
- scalar сохраняет текущую политику `fmtNum()`;
- внутренние вычисления выполняются с полной точностью `Number`;
- деление на ноль возвращает ошибку, а не `Infinity`.

Для текущего масштаба новый decimal-пакет не нужен. Если позднее появятся налоги, банковское округление или длинные цепочки денежных операций, денежную ветку можно перевести на целые минимальные единицы либо decimal-библиотеку.

## 6. Архитектура

### Не изменять существующий `calc()` в первой итерации

`calc()` уже используется обычными формулами, переменными и депозитом. Его переписывание расширит область регрессий. Новый typed-калькулятор лучше добавить рядом:

```text
notatnyk-tauri/src/quantity-calc.js
BitrixUI/frontend/src/lib/quantityCalc.ts
```

Рекомендуемый публичный контракт:

```ts
type QuantityCalcErrorCode =
  | "quantity_syntax_error"
  | "quantity_unknown_variable"
  | "quantity_unit_mismatch"
  | "quantity_invalid_operation"
  | "quantity_division_by_zero";

type QuantityCalcResult =
  | {
      ok: true;
      source: string;
      value: CalcValue;
      start: number;
      end: number;
    }
  | {
      ok: false;
      code: QuantityCalcErrorCode;
      start: number;
      end: number;
    };

parseQuantityExpression(source, resolveVariable): QuantityCalcResult | null
```

Разделить обязанности:

1. lexer создаёт токены и позиции в исходной строке;
2. parser строит небольшое дерево выражения;
3. evaluator применяет правила типов и возвращает `CalcValue`;
4. formatter форматирует число и единицу;
5. адаптер `inline()` превращает результат в HTML и решает, входит ли он в Σ.

Ни lexer, ни evaluator не должны знать о CSS, HTML, режиме клиента или `deal.amount`.

### Извлечение выражения из строки

Typed-выражение обрабатывается только после введённого завершающего `=`. Незавершённая запись во время набора не должна мигать ошибкой или частично вычисляться.

Первая версия может консервативно искать выражение, которое заканчивается последним `=` в inline-фрагменте. Допускается текстовый префикс:

```text
Скидка: 3720 грн - 10% =
Тираж после брака: 100 шт - 3% =
```

Парсер выбирает самый длинный валидный суффикс, начинающийся с числа или числовой переменной. Формулы внутри backtick-кода, URL и размерных токенов не рассматриваются.

## 7. Интеграция в `inline()`

Новый порядок обработки в обоих движках:

```text
сырой inline-текст
→ защитить `inline code`
→ найти и вычислить quantity expressions
→ заменить их безопасными placeholders
→ экранировать оставшийся пользовательский текст
→ обработать размеры, обычные цены, старые calc и переменные
→ восстановить HTML quantity expressions
→ применить остальную инлайн-разметку
```

Это гарантирует, что:

- `3720 грн` не будет превращено в price HTML раньше вычисления;
- `2` из `м2` не станет началом старой формулы;
- результат не будет повторно распознан как новая цена;
- единица и исходная формула экранируются до вставки в HTML;
- выражение учитывается в Σ ровно один раз.

### Расширенный результат `inline()`

Полезно добавить контекст и метаданные:

```ts
type InlineContext = "body" | "total";

type InlineResult = {
  html: string;
  sum: number;
  terminalQuantity?: CalcValue;
  diagnostics?: SpecDiagnostic[];
};

inline(text, { context: "body" })
```

`terminalQuantity` — результат выражения, заканчивающего inline-фрагмент. Он нужен строке `Итого`, чтобы объявленным значением было вычисленное число, а не первый операнд.

## 8. Правила денежной Σ и `Итого`

### Обычная строка

- результат имеет `unitKey === normalizeUnit(LOCALE.currency)` — добавить результат в Σ;
- единица вида `грн/шт` или любая другая — показать, но не добавлять в денежную Σ;
- исходная базовая сумма внутри выражения отдельно в Σ не входит;
- одно выражение добавляется не более одного раза.

Пример:

```text
Печать со скидкой: 3720 грн - 10% =
```

Добавляет в Σ `3348`, а не `3720`, `0,1` или `7068`.

### Строка `Итого:`

Вызывать:

```ts
inline(rest, { context: "total" })
```

Правила:

- выражение не добавляется в `sectionSum`;
- если `terminalQuantity` имеет единицу текущей валюты, его значение становится `declaredHere`;
- если подходящего результата нет, остаётся старый разбор первого денежного числа;
- сравнение `sectionSum` выполняется с вычисленным итогом;
- `lastTotal` также получает вычисленный итог;
- выражение с невалютной единицей рендерится, но не становится денежным `declared`.

Таким образом:

```text
= 3348 грн
Итого: 3720 грн - 10% =
```

даёт `sectionSum = 3348`, `declared = 3348` и успешную сверку.

## 9. Режимы отображения

### Авторский просмотр

Показывать исходную формулу и результат:

```text
3720 грн − 10% = 3 348,00 грн
```

Для HTML переиспользовать существующие классы:

- исходник — `calc-formula`;
- знак равенства — `calc-eq`;
- результат в валюте обычной строки — `price-sum`;
- результат с иной единицей — `calc-res`.

Новые CSS-классы не нужны, пока существующего оформления достаточно.

### Клиентский режим / экспорт

Формулу скрывать по текущему правилу и показывать только результат:

```text
= 3 348,00 грн
```

BitrixUI использует `renderForClient()`, Notatnyk — export mode. Формирование HTML результата должно получать явный `mode`, а не читать его внутри математического ядра.

### Построчный редактор

`inlineSource()` и `renderSourceLines()` должны распознавать всё выражение как единый синтаксический фрагмент, но не менять исходный текст и не вставлять вычисленный результат в редактируемую строку.

Это необходимо для инвариантов caret/undo и устраняет текущую ошибочную подсветку `2 + 10%` внутри `50 м2 + 10% =`.

## 10. Диагностика

Показывать диагностику только если пользователь закончил кандидат символом `=`. Незавершённый ввод не является ошибкой.

| Код | Пример | Сообщение |
|---|---|---|
| `quantity_unit_mismatch` | `50 шт + 2 кг =` | Нельзя сложить `шт` и `кг` |
| `quantity_invalid_operation` | `2 м * 3 м =` | Умножение двух величин пока не поддерживается |
| `quantity_division_by_zero` | `50 шт / 0 =` | Деление на ноль |
| `quantity_unknown_variable` | `[остаток] шт + 2 шт =` | Неизвестная переменная `[остаток]` |
| `quantity_syntax_error` | `50 шт + =` | Не удалось завершить вычисление |

В авторском режиме диагностике передаётся номер строки. В клиентском режиме внутренние ошибки не отображаются, но могут оставаться в массиве `diagnostics`, чтобы карточка сделки не потеряла сигнал готовности.

Не добавлять диагностику для обычного текста с `=` без сильного признака quantity expression.

## 11. Обратная совместимость

Обязаны продолжить работать:

```text
2*3=
3720-10%=
3720 - 10% = грн
= 500 грн
500 грн/шт
[цена] = 100*2
= [цена] грн
```

Новый typed-parser запускается раньше старого, но забирает только выражения, содержащие распознанную единицу. Если он возвращает `null`, строка проходит существующий pipeline без изменений.

`calc()` и правила переменных/депозита в первой версии не меняются.

### Интеграционные contract-fixtures

Расширить существующий `spec-fixtures.json` минимум следующими случаями:

1. `50 шт + 50 шт =` → `100 шт`;
2. `3720 грн - 10% =` → `3348,00 грн`, total `3348` в обычной строке;
3. `= 3348 грн\nИтого: 3720 грн - 10% =` → declared и section sum `3348`;
4. `50 м2 + 10% =` → `55 м2`, а не `2,2`;
5. `5 автомобилей - 10% =` → `4,5 автомобилей`;
6. `100 A3+ - 10% =` → единица `A3+`;
7. `10 грн/шт - 10% =` → результат не входит в Σ;
8. `50 шт + 2 кг =` → текст сохранён и есть diagnostic;
9. выражение внутри backticks не вычисляется;
10. незавершённая строка без `=` не выдаёт diagnostic;
11. неизвестная числовая переменная;
12. клиентский режим не содержит исходной формулы;
13. старый формат `3720 - 10% = грн` не изменился;
14. HTML внутри единицы безопасно экранирован.

Harness следует расширить проверками `diagnosticsExclude` и, при необходимости, точного количества срабатываний, чтобы исключить двойное добавление в Σ.

1. Перенести чистое ядро один в один с типами.
2. Прогнать те же pure fixtures.
3. Повторить интеграцию в `specEngine.ts`.
4. Проверить `render()`, `renderForClient()` и `renderSourceLines()`.
5. Убедиться, что `stats.total` корректно сравнивается с `deal.amount`.

### Этап E — документация и выпуск

1. Обновить подсказки синтаксиса в обоих продуктах.
2. Поднять `SPEC_SYNTAX_VERSION` с `1.1.0` до `1.2.0` одновременно.
3. Проверить идентичность двух JSON-fixtures.
4. Сначала выпустить Notatnyk или тестовую сборку BitrixUI, затем проверить реальные ТЗ.
5. Не включать конвертацию единиц до появления подтверждённых пользовательских сценариев.

## 15. Риски и защита от них

| Риск | Защита |
|---|---|
| Парсер захватывает обычный текст | Завершающий `=`, валидная typed-грамматика, all-or-nothing |
| `м2` превращается в число `2` | Typed extraction выполняется раньше старого калькулятора |
| Цена попадает в Σ дважды | Placeholder скрывает всё выражение от `RE.price`; отдельный тест количества |
| `Итого` остаётся равным первому операнду | Использовать `terminalQuantity.value` как declared |
| Две реализации расходятся | Общие pure и integration fixtures, синхронная версия синтаксиса |
| Сломан старый депозит или переменные | Не менять `calc()` на первом этапе |
| Единица внедряет HTML | Парсить сырой текст, рендерить только через `esc()` |
| Редактор меняет исходник | `renderSourceLines()` только подсвечивает, не записывает результат в source |
| Неожиданное округление количества | Валюта — 2 знака; прочее — до 6, правило покрыто тестами |

## 16. Критерии готовности

- `Итого: 3720 грн - 10% =` показывает `3 348,00 грн`, а не `0,1`.
- `50 шт + 50 шт =` показывает `100 шт`.
- Любая совместимая произвольная единица сохраняется без словаря.
- Несовместимые единицы не вычисляются и дают понятную диагностику.
- Результат валютной формулы входит в Σ один раз.
- В строке `Итого` вычисленный результат используется как declared и сверяется с секцией.
- Произвольные единицы не влияют на денежную сумму сделки.
- Автор видит формулу, клиент — только результат.
- Исходный текст, caret, undo и сохранение поля не меняются рендерером.
- Старые формулы, цены, переменные и депозит проходят без изменений.
- Pure fixtures и contract-fixtures идентичны и зелёные в обоих проектах.
- `SPEC_SYNTAX_VERSION` совпадает в Notatnyk и BitrixUI.

## 17. Оценка

При сохранении описанного объёма:

- контракт и fixtures — 0,5 дня;
- чистое JS-ядро и тесты — 0,5–1 день;
- интеграция Notatnyk — 0,5–1 день;
- TS-порт и интеграция BitrixUI — 0,5–1 день;
- ручная проверка, документация и исправление краёв — 0,5 дня.

Итого: ориентировочно 2,5–4 рабочих дня. Автоконвертация единиц, склонение и производные физические размерности сознательно не входят в эту оценку.
