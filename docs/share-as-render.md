# Share-as-Render — техническая схема

> Как отдать клиенту **только отрендеренный результат**, физически не передавая ему
> формулы, переменные и скрытую себестоимость — при этом автор считает локально
> с любого устройства, быстро делится в облако и легко перегенерирует по новым вводным.
> Каждый рендер несёт **версию, дату/время правки и подпись-хеш**, по которой всегда
> можно поднять исходную калькуляцию для проверки.

Статус: дизайн v1. Опирается на существующую модель Notatnyk (`.md`-first, скрытые
строки `//` и блоки `/* */`, движок в `src/parser.js`). Принцип проекта — **лёгкость,
простота, надёжность** ([[keep-it-lightweight]]) — здесь ведущий: криптография
берётся готовая, никакого своего «крипто-велосипеда».

---

## 0. Словарь

| Термин | Что это |
|---|---|
| **Source (исходник)** | Обычная заметка `.md`: формулы, переменные, скрытая себестоимость, разметка. Единственный источник истины. Живёт локально. |
| **Render (рендер)** | Публичный результат: только то, что должен видеть клиент. Формул внутри нет — они удалены, а не спрятаны. |
| **Manifest** | Маленький JSON-паспорт публикации: версия, время, хеши, подпись автора. |
| **Publish (публикация)** | Операция: из source → (render + manifest), опционально запечатанная копия source, загрузка в облако, получение ссылки. |
| **Author key** | Ключевая пара автора (Ed25519). Подписывает публикации. Даёт «этот расчёт сделал я». |
| **Sealed source** | Зашифрованная копия исходника для аудита/перегенерации. Клиенту не отдаётся никогда. |

---

## 1. Главный принцип: разделение, а не сокрытие

Ключевая ошибка конкурентов и веб-калькуляторов — они **прячут** формулы (CSS
`display:none`, скрытые поля формы, JS-переменные). Всё это лежит в payload и
достаётся из devtools за 10 секунд.

Notatnyk делает иначе: **на устройстве автора source компилируется в render, и в
render физически нет исходных формул**. Клиент получает документ, в котором нечего
раскрывать — там нет секретов ни в DOM, ни в JS, ни в сети.

```
        УСТРОЙСТВО АВТОРА (доверенная зона)         │   ОБЛАКО / КЛИЕНТ (недоверенная зона)
                                                    │
  source.md ──►  движок парсера  ──►  render.json   │
  (формулы,        (compute)          (только       │
   переменные,                        числа+текст,  │
   // скрытое)                        без формул) ───┼──►  https://ntk.app/r/<id>
        │                                           │         рендерит статичную
        └──► seal() ──► source.md.enc ──────────────┼──►  страницу. В payload —
             (шифр, ключ у автора)                  │     НИ ОДНОЙ формулы.
                                                    │
                                                    │     source.md.enc лежит рядом,
                                                    │     но зашифрован и НЕ отдаётся
                                                    │     в ответе клиенту.
```

Граница доверия проходит по стрелке «загрузка в облако». Всё, что пересекает её в
сторону клиента, уже обеззаражено.

## 2. Модель данных исходника

Source остаётся **одним `.md` файлом** — как сейчас (см. [[notatnyk-storage-format]]),
без сайдкаров. Расширяем только необязательным YAML-фронтматтером для метаданных
публикации. Нет фронтматтера → заметка просто не опубликована, всё как раньше.

```markdown
---
ntk:
  id: 9f3a1c            # стабильный id заметки (генерится при первой публикации)
  author: ed25519:Ab12…9Zx   # публичный ключ автора (author id)
  version: 3            # монотонно растущий номер версии публикации
  published_at: 2026-07-16T14:23:07+03:00
  source_hash: blake3:7d1e…            # хеш канонизированного исходника (см. §6)
  visibility:           # что попадает в render
    hide_comments: true       # строки // и блоки /* */ вырезаются (по умолчанию true)
    hide_math_source: true    # показывать только результат "= 272,1", не выражение
    hide_unit_costs: false    # прятать ли строки грн/шт
---
# Книжный клуб — закладки
Дата: [date]

## Т.З.
| Описание | Значение |
| размер   | 57x175mm |

// себестоимость печати, клиенту не показываем
// печать = 18400/1200*1125 = грн
- печать (для клиента: «полиграфия») = 18400/1200*1125 = грн
Итого: = грн [4000 шт]
```

Важно: **источник истины — тело `.md`**. Фронтматтер `ntk:` — это кэш последней
публикации, он перегенерируется при каждом publish и никогда не редактируется руками.

### Уровни видимости в тексте

Три существующих/новых механизма, по возрастанию скрытности:

1. `// строка` и `/* блок */` — **уже есть**. Не попадают в render, но считаются в Σ.
   Это «внутренняя кухня» (себестоимость, заметки для себя).
2. `hide_math_source` — в render уходит только результат `272,1`, а не выражение
   `55*3+7*(2.5+3.5)*2.55`. Клиент видит цифру, не видит, как она получена.
3. Переменные `#{ставка} = 18400` — объявления переменных всегда режутся из render;
   в результат подставляется вычисленное значение. (Расширение движка, см. §9.)

## 3. Что такое Render и почему он безопасен

Render — это **не HTML со спрятанными кусками**, а самостоятельный минимальный
документ, собранный из «разрешённых» узлов AST.

Формат — `render.json` (компактный, легко кэшировать и подписывать):

```json
{
  "schema": "ntk-render/1",
  "id": "9f3a1c",
  "version": 3,
  "published_at": "2026-07-16T14:23:07+03:00",
  "title": "Книжный клуб — закладки",
  "blocks": [
    { "t": "quote", "text": "Нужны премиальные закладки, софт-тач, тираж 4000.", "client": "Книжный клуб" },
    { "t": "h2", "text": "Т.З." },
    { "t": "table", "rows": [["Описание","Значение"],["размер","57x175mm"]] },
    { "t": "li", "text": "печать (полиграфия)", "value": "17 250 грн" },
    { "t": "total", "label": "Итого", "value": "54 980 грн", "per_unit": "13,75 грн/шт" }
  ],
  "author": "ed25519:Ab12…9Zx",
  "source_hash": "blake3:7d1e…",
  "render_hash": "blake3:44c0…",
  "sig": "ed25519:9aa2…"
}
```

Как это строится (в `src/parser.js`, на устройстве автора):

```
parse(source.md)          → AST со ВСЕМИ узлами (формулы, // скрытое, переменные)
   │
compute(AST)              → вычисляет значения (Σ, Итого, калькулятор, per-unit)
   │
project(AST, visibility)  → НОВОЕ дерево: берём только визуальные узлы и вычисленные
   │                        значения; узлы-формулы/скрытое/переменные ОТБРАСЫВАЕМ
render.json               → сериализация обеззараженного дерева
```

`project()` — ключевая функция безопасности. Правило простое: **в render.json
попадает только то, что явно разрешено (allowlist), а не «всё кроме скрытого»
(denylist).** Allowlist невозможно случайно «пробить» новым синтаксисом: незнакомый
узел по умолчанию не проходит.

Гарантии для клиента:

- В `render.json` нет строк-выражений (только результаты), нет `//`/`/* */`, нет
  объявлений переменных.
- Публичная страница `ntk.app/r/<id>` — статический рендер этого JSON. Ни исходник,
  ни `source.md.enc` в её сетевых запросах не участвуют.
- Devtools показывает ровно то, что видит глаз: числа и текст. Раскрывать нечего.

## 4. Публикация и передача клиенту

### 4.1. Локальный (офлайн) обмен — бесплатный tier

Кнопка «Экспорт рендера» → один файл `<title>.ntkr` (это просто `render.json`,
можно завернуть в самодостаточный `.html` для просмотра без приложения). Отдаёшь
клиенту как файл. Формул внутри нет по построению (§3).

### 4.2. Облачная ссылка — платный tier

```
Автор жмёт «Поделиться»
   │
   ├─ project()+compute()  →  render.json         (публичный)
   ├─ seal(source.md)      →  source.md.enc        (приватный, ключ у автора)
   ├─ build manifest       →  manifest.json        (версия, хеши, подпись)
   │
   └─ PUT в облако:
        r/<id>/v3/render.json     ← отдаётся клиенту по ссылке (public read)
        r/<id>/v3/manifest.json   ← отдаётся клиенту (для проверки подписи)
        r/<id>/v3/source.md.enc   ← private: read только по auth автора
        r/<id>/latest → v3        ← указатель «текущая версия» (см. §5)
   →  ссылка: https://ntk.app/r/9f3a1c
```

Разделение бакета по правам доступа — вторая линия обороны: даже если клиент угадает
URL `source.md.enc`, облако вернёт 403; а если и скачает — там шифртекст без ключа.

### 4.3. Что именно уходит клиенту

| Артефакт | Клиент получает? | Содержит формулы? |
|---|---|---|
| `render.json` | ✅ да | ❌ нет (по построению) |
| `manifest.json` | ✅ да | ❌ нет (только хеши/подпись) |
| `source.md.enc` | ❌ нет (403 + шифр) | (зашифрован) |
| ключ шифрования | ❌ никогда | — |

## 5. Версионирование

### 5.1. Модель версий

Каждая публикация иммутабельна и адресуется по версии:

```
r/9f3a1c/
   v1/  (render.json, manifest.json, source.md.enc)   — 12.07.2026
   v2/  …                                              — 14.07.2026
   v3/  …                                              — 16.07.2026
   latest → v3
```

- **Иммутабельность**: `v1`, `v2` никогда не меняются. Клиент, которому дали ссылку
  на конкретную версию (`/r/9f3a1c/v2`), всегда видит ровно то, что видел.
- **Указатель `latest`**: ссылка `/r/9f3a1c` резолвится в `latest`. Перегенерация по
  новым вводным (см. §7) двигает указатель, старые версии остаются для аудита.
- Автор выбирает при шеринге: «ссылка на конкретную версию» (замороженная смета) или
  «ссылка на актуальную» (живой прайс, обновляется при правках).

### 5.2. Версия в самом рендере

Футер публичной страницы и `.ntkr` всегда показывает штамп:

```
────────────────────────────────
v3 · 16.07.2026 14:23 · #7d1e44c0 · ✔ подпись автора Ab12…9Zx
```

- `v3` — номер версии.
- `16.07.2026 14:23` — `published_at` (время последней правки/перегенерации).
- `#7d1e44c0` — короткий префикс `source_hash` (8 hex). По нему поднимается исходник (§8).
- `✔ подпись` — результат проверки `sig` против `author` прямо на странице.

Дата/время берём из момента публикации, а не из mtime файла: так значение стабильно
переживает синк между устройствами (mtime у Dropbox/iCloud «плывёт»).

### 5.3. Цепочка версий (tamper-evident)

В manifest каждой версии кладём `prev_hash` — хеш предыдущего manifest. Получается
хеш-цепочка: любую версию можно проверить на непрерывность истории, задним числом
вставить/подменить версию нельзя без пересборки всей цепочки (а её подписывает только
автор своим ключом).

```json
// manifest.json (v3)
{
  "id": "9f3a1c",
  "version": 3,
  "published_at": "2026-07-16T14:23:07+03:00",
  "author": "ed25519:Ab12…9Zx",
  "source_hash": "blake3:7d1e…",
  "render_hash": "blake3:44c0…",
  "sealed_source_hash": "blake3:e5b7…",   // хеш source.md.enc
  "prev_hash": "blake3:1122…",            // хеш manifest v2 (null для v1)
  "sig": "ed25519:9aa2…"                  // подпись над всем вышестоящим
}
```

Подпись `sig` покрывает всё поле manifest, то есть **связывает воедино**: версию,
время, исходник, рендер и запечатанный исходник. Нельзя показать клиенту один рендер,
а «на проверку» подсунуть другой исходник — хеши не сойдутся, подпись отвалится.

## 6. Хеширование и канонизация

Чтобы `source_hash` был воспроизводимым на любом устройстве и в любой ОС, хешируем не
байты файла, а **канонизированный исходник**:

1. Нормализовать переводы строк в `\n`.
2. Убрать трейлинг-пробелы в конце строк, финальный перевод строки — ровно один.
3. Убрать из хеша сам блок фронтматтера `ntk:` (он производный — иначе рекурсия).
4. Пин вычислений: рядом с телом хешируем `computed`-снимок (значения переменных,
   курсы валют на момент публикации) — чтобы «тот же текст, но другой курс доллара»
   давал другой хеш и другую версию. Курс/константы фиксируются в manifest.

```
source_hash = blake3( canonical_body || "\x00" || canonical_computed_snapshot )
render_hash = blake3( canonical(render.json without sig) )
```

Алгоритм — **BLAKE3** (быстрый, есть в Rust `blake3` crate, для лёгкого приложения
идеально). Подписи — **Ed25519** (`ed25519-dalek`). Шифрование sealed source —
**XChaCha20-Poly1305** (`chacha20poly1305`). Всё это — небольшие проверенные крейты,
никакой своей крипты.

## 7. Перегенерация по новым вводным

Сценарий: «тираж не 4000, а 6000 — пересчитай и обнови ссылку».

```
1. Автор открывает source.md (локально, на любом устройстве).
2. Меняет вводные: правит переменные / количество [6000 шт] / цены.
3. Движок мгновенно пересчитывает (как сейчас, на лету).
4. «Опубликовать обновление»:
     version := version + 1
     compute() → project() → новый render.json
     seal(source) → новый source.md.enc
     manifest(prev_hash = хеш прошлого manifest) → подпись
     PUT r/<id>/v4/*  ;  latest → v4
5. Клиент по старой ссылке /r/<id> видит уже v4:
     обновлённые числа, новый штамп «v4 · дата · #hash».
```

Ключевая выгода перед конкурентами: **вводные — это переменные в исходнике**, поэтому
перегенерация = правка одной строки + кнопка, а не пересбор документа. Автор не
трогает вёрстку и текст для клиента — только цифры.

Опционально: «черновой пересчёт» — пересчитать и посмотреть новый render локально, не
публикуя (не двигая `latest`), пока не устроит результат.

## 8. Проверка подлинности и поднятие исходника

Задача: по штампу `#7d1e44c0` (или по ссылке) **доказать, что показанный клиенту
рендер получен именно из конкретного исходника**, и при споре поднять исходник.

### 8.1. Публичная проверка (может любой, у кого есть ссылка)

На странице рендера кнопка «Проверить»:

1. Скачать `render.json` + `manifest.json`.
2. Пересчитать `render_hash` из `render.json` → сверить с manifest.
3. Проверить `sig` над manifest публичным ключом `author` (Ed25519).
4. Проверить `prev_hash`-цепочку до v1.

Результат: «этот рендер v3 создан владельцем ключа Ab12…9Zx 16.07.2026 и не изменён».
Клиент **не** получает исходник, но получает математическую гарантию целостности и
авторства. Это то, чего нет ни у кого в лёгком классе.

### 8.2. Аудит с раскрытием исходника (только автор / доверенный аудитор)

Когда нужно доказать *как* считалось (спор с заказчиком, налоговая, партнёр):

```
1. По #hash находим версию: source_hash → v3.
2. Автор авторизуется в облаке (его ключ) → скачивает source.md.enc.
3. decrypt(source.md.enc, author_key) → source.md.
4. Проверка: blake3(canonical(source)) == manifest.source_hash ?  → исходник подлинный.
5. Локальный пересчёт: project(compute(parse(source))) → render'.
   render_hash(render') == manifest.render_hash ?  → рендер честно выведен из исходника.
```

Итог цепочки доверия:

```
подпись автора ──► manifest ──► source_hash ──► источник ──► пересчёт ──► render_hash
     (кто)          (когда)      (что считал)    (открыли)    (проверили)  (что показал)
```

По желанию — режим «раскрытие по требованию»: автор выдаёт аудитору одноразовый
ключ на конкретную версию (не на весь аккаунт), тот проверяет п.3–5 сам.

## 9. Личность автора и мульти-устройство

### 9.1. Ключ автора

- При первом запуске генерится пара **Ed25519**. Приватный ключ — в системном
  хранилище (Keychain / Windows Credential Manager / Android Keystore), не в `.md`.
- Публичный ключ = **author id**, светится в рендере и manifest.
- Перенос на второе устройство: экспорт ключа, обёрнутого парольной фразой
  (Argon2id → ключ обёртки), через QR-код или файл. Импорт на новом устройстве.
- Потеря ключа = потеря права публиковать *под этим id* (старые публикации остаются
  валидными и проверяемыми). Рекомендуем «recovery-фразу» при заведении ключа.

### 9.2. Локально-первичная работа с разных устройств

Источник истины — `.md` в выбранной папке (уже поддержано, [[notatnyk-storage-format]]).
Два пути синка исходников между своими устройствами:

| Путь | Как | Кому |
|---|---|---|
| **Своя папка** | Папка заметок лежит в Dropbox/iCloud/Syncthing. Notatnyk просто читает/пишет `.md`. Ноль нашего облака. | Бесплатный tier, приватность-максимум. |
| **Наш sync** | Мы храним `source.md.enc` (E2E, ключ у автора) и синхроним между устройствами автора. | Платный tier, удобство. |

В обоих случаях **публикация подписывается ключом автора**, поэтому неважно, с какого
устройства опубликовано — подпись сходится, версия монотонна (номер версии берём как
`max(known)+1`; при гонке двух устройств — разрешаем по времени+хешу, конфликт
показываем автору, а не молча теряем правку).

Разметка кнопки: **локальная версия первична и бесплатна** — облако/подпись включаются
только когда автор осознанно жмёт «Поделиться».

## 10. Модель угроз (что клиент может и НЕ может)

| Клиент/злоумышленник хочет… | Результат |
|---|---|
| Открыть devtools и найти формулу | ❌ Их нет в payload. Только числа/текст. |
| Скачать `source.md.enc` по прямому URL | ❌ 403 (private); а если утёк — шифртекст без ключа. |
| Подменить число в рендере и показать другому | ❌ `render_hash`/`sig` не сойдутся при «Проверить». |
| Выдать чужой расчёт за расчёт автора | ❌ Нет приватного ключа автора — подпись не подделать. |
| Вставить фейковую версию в историю | ❌ Хеш-цепочка `prev_hash` + подпись рвётся. |
| Реверснуть формулу из чисел | ⚠️ Только угадать (это уже не утечка исходника, а домысел). |

Чего схема **не** обещает: скрыть *результаты* (они по определению показаны клиенту) и
защитить от автора, который сам решил показать формулу. Мы защищаем исходник, не
арифметику на виду.

## 11. Что трогаем в коде (реализация, поэтапно)

Опираемся на текущую структуру: `src/parser.js` (движок), `src/main.js` (UI),
`src-tauri` (Rust: файлы, теперь ещё крипта и загрузка).

**Этап 1 — фундамент рендера (бесплатный, офлайн):**
- `parser.js`: выделить `compute()` и добавить `project(ast, visibility)` (allowlist).
- Сериализация `render.json` + экспорт `.ntkr`/самодостаточный `.html`.
- Футер-штамп версии/даты/хеша (пока без облака: версия локальная, хеш — BLAKE3 в Rust).
- Rust: команда `hash_source`, `export_render`.

**Этап 2 — подпись и версии (бесплатный, локальный):**
- Rust: генерация/хранение Ed25519 (keychain-крейт), `sign_manifest`, `verify`.
- Фронтматтер `ntk:` в `.md`, канонизация (§6), цепочка `prev_hash`.
- Кнопка «Проверить» для `.ntkr` (офлайн-проверка подписи).

**Этап 3 — облако и ссылка (платный):**
- `seal()`/`unseal()` (XChaCha20-Poly1305) в Rust.
- Загрузка `render.json`/`manifest.json`/`source.md.enc` в объектное хранилище с
  раздельными правами; указатель `latest`.
- Публичная страница `/r/<id>` (статический рендер `render.json` + «Проверить»).
- Перегенерация (§7), выбор «версия/актуальная», аудит-раскрытие (§8.2).

**Этап 4 — мульти-устройство и настройки (платный):**
- Экспорт/импорт ключа (QR + Argon2id), наш E2E-sync исходников.
- Тонкие настройки видимости (`hide_math_source`, `hide_unit_costs`, переменные `#{}`).

## 12. Открытые вопросы (решить до Этапа 3)

1. **Объектное хранилище**: свой сервер + S3-совместимое (MinIO/Cloudflare R2) или
   managed (Supabase Storage)? Критерий — лёгкость и цена на idle, а не фичи.
2. **Короткие id**: `9f3a1c` — коллизии на масштабе; закладываем 8–10 симв. base32
   + проверку уникальности при первой публикации.
3. **Отзыв ссылки**: удаление `latest` + tombstone; иммутабельные версии оставляем
   для аудита или тоже физически чистим по GDPR-запросу?
4. **Курсы валют**: где брать и как пинить в `computed`-снимок, чтобы перегенерация
   на другом курсе была явной новой версией, а не «тихо поплывшими» цифрами.
5. **Формат `.ntkr`**: голый JSON (для приложения) vs самодостаточный HTML (для того,
   у кого приложения нет). Вероятно, оба; HTML — обёртка над тем же JSON.

### TL;DR

- **Исходник никогда не превращается в «спрятанный» — он остаётся на устройстве
  автора; клиенту уходит отдельно собранный обеззараженный render** (allowlist, §3).
- **Каждая публикация подписана Ed25519 и адресуется версией**; штамп в рендере несёт
  `версию · дату/время · #hash · ✔ подпись` (§5).
- **По `#hash` поднимается иммутабельный исходник для аудита** (§8), а публичную
  целостность/авторство любой проверяет без доступа к исходнику.
- **Перегенерация = правка вводных-переменных + кнопка** (§7); локальная работа
  первична и бесплатна, облако/подпись — по кнопке «Поделиться» (§9).
