# Отчёт по реализации калькулятора величин

Дата аудита: 06.09.2026

Область:

- Notatnyk, коммит `831b5c9 feat(calc): quantity-aware calculator for arbitrary units`;
- BitrixUI, коммит `127281b feat(spec): quantity-aware calculator for arbitrary units`;
- общий контракт, статистика Σ, строки `Итого`/`Разом`, рабочий и клиентский рендер;
- построчный редактор и влияние на карточку сделки.

## 1. Итог аудита

Архитектурное направление верное: typed-калькулятор вынесен из старого `calc()`, работает до денежного рендера и закрывает исходный дефект `3720 грн - 10% = → 0,1`. JS- и TS-реализации хорошо синхронизированы, тесты проходят, текущая производительность достаточна.

Но реализацию пока нельзя считать полностью завершённой. Главная проблема находится не в арифметике, а в общей семантике денег:

```text
сумма позиций 3720 грн
Итого: 3720 грн - 10% = 3348 грн
```

Парсер получает правильный результат `3348`, но:

- `stats.total` остаётся `3720`;
- строка `Итого` сравнивает сумму позиций с результатом после скидки и показывает ложное расхождение;
- BitrixUI сравнивает `deal.amount` с `3720`, а не с `3348`;
- typed-формула в валюте не увеличивает `stats.positions`, поэтому итоговый блок карточки иногда вообще скрывается.

Вторая группа рисков — несколько выражений вычисляются неверно вместо безопасного отказа. Наиболее опасный пример:

```text
-5 грн + 10 грн =
```

Сейчас результатом становится `15 грн`, потому что унарный минус остаётся за пределами найденного выражения.

Вывод: порядок стадий парсинга сохраняем, полный parser rewrite не нужен. Сначала необходимо исправить модель `gross/effective total` и случаи молчаливо неверного результата, затем выровнять обещанную грамматику и убрать повторные проходы.

## 3. Что реализовано правильно

### Разделение ответственности

Созданы отдельные чистые ядра:

```text
notatnyk-tauri/src/quantity-calc.js
BitrixUI/frontend/src/lib/quantityCalc.ts
```

Старый `calc()` не переписан. Это защищает обычные формулы, переменные и депозит от лишних регрессий.

### Порядок inline-разбора

Текущий верхнеуровневый порядок правильный:

```text
маскирование `code` и размерных токенов
→ typed quantity parse на сыром тексте
→ безопасный placeholder
→ HTML escaping
→ габариты
→ обычные цены
→ старый calc()
→ переменные и стили
→ восстановление готового quantity HTML
```

Именно такое расположение не позволяет `RE.price` раньше времени превратить `3720 грн` в HTML и не даёт цифре `2` из `м2` стать самостоятельной формулой.

### Типы и операции

Корректно реализованы:

- сложение и вычитание одинаковых однословных единиц;
- прибавление/вычитание процента от текущего значения;
- умножение величины на scalar;
- умножение scalar на величину;
- деление величины на scalar;
- умножение на процент;
- отказ при разных единицах, делении на ноль и `quantity × quantity`;
- фиксированные два десятичных знака для configured currency;
- исключение `грн/шт` и других единиц из денежной Σ;
- скрытие формулы в клиентском режиме;
- экранирование единицы перед вставкой в HTML;
- сохранение старого формата `3720 - 10% = грн`.

### Синхронизация портов

`SPEC_SYNTAX_VERSION`, pure fixtures и integration fixtures поддерживаются параллельно. Этот механизм следует сохранить как обязательное условие любого изменения грамматики.

## 4. Целевая денежная семантика

Сейчас слово `total` используется сразу для двух разных смыслов. Их необходимо разделить.

### Определения

```ts
type SectionTotals = {
  gross: number              // сумма позиций секции до скидок/коррекций
  checkBase: number | null   // число, с которым должна совпасть gross
  declared: number | null    // явно объявленный/вычисленный итог
  effective: number          // итог секции после корректировки
  line: number
}

type SpecStats = {
  grossTotal: number         // сумма всех денежных позиций
  effectiveTotal: number     // сумма, которая должна совпасть с deal.amount
  total: number              // временный compatibility alias, см. миграцию ниже
  positions: number
  declared: number | null
  sections: SectionTotals[]
}
```

### Обычный подытог

```text
= 1000 грн
= 500 грн
Итого: 1500 грн
```

Результат:

```text
gross      = 1500
checkBase  = 1500
declared   = 1500
effective  = 1500
```

### Подытог со скидкой

```text
= 2000 грн
= 1720 грн
Итого: 3720 грн - 10% =
```

Результат:

```text
gross      = 3720
checkBase  = 3720   // первый денежный operand формулы
declared   = 3348   // результат формулы
effective  = 3348
```

Зелёная проверка отвечает на вопрос: «Правильную ли базу мы корректируем?» Поэтому сравнивать нужно `gross` с `checkBase`, а не с `declared`.

### Ошибка формулы

```text
= 50 грн
Итого: 50 грн + 2 кг =
```

Результат:

```text
gross      = 50
checkBase  = null
declared   = null
effective  = 50     // безопасный fallback только для статистики
status     = error
```

Зелёный `✓` при наличии quantity diagnostic запрещён.

### Незакрытая последняя секция

Если после последнего `Итого` остаются денежные позиции, они добавляются в `grossTotal` и `effectiveTotal` без выдуманного declared.

## 5. P0 — исправления до использования в сделках

### P0.1. Итог после скидки не используется при сравнении с заказом

Текущее место:

```text
BitrixUI/frontend/src/components/SpecChecklist.tsx
```

Сейчас `matches` и вывод суммы используют `stats.total`. Нужно перевести их на `stats.effectiveTotal`:

```ts
const payable = stats.effectiveTotal
const matches = hasOrder && Math.abs(payable - orderAmount) < 0.5
```

В UI желательно показывать оба значения только когда они различаются:

```text
Σ позиций: 3 720 грн · Итого после скидки: 3 348 грн
```

Когда значения одинаковы, достаточно одного итога.

### P0.2. Ложный mismatch для корректной скидки

Текущие места:

```text
notatnyk-tauri/src/parser.js       ветка RE.totalLine
BitrixUI/frontend/src/lib/specEngine.ts ветка RE.totalLine
```

`parseQuantityExpression()` должен вернуть не только итог, но и первую величину либо структурированную базу:

```ts
type QuantityCalcSuccess = {
  ok: true
  value: CalcValue
  firstQuantity: CalcValue | null
  start: number
  end: number
}
```

Для `3720 грн - 10%`:

```text
firstQuantity.value = 3720
value.value         = 3348
```

Ветка `RE.totalLine` сравнивает `sectionSum` с `firstQuantity.value`, а `declared/effective` получает из `value.value`.

### P0.3. Ошибочный `Итого` показывает зелёный `✓`

Текущая логика при отсутствии успешного `terminalQuantity` берёт первое число строки. Это допустимо для обычного `Итого: 500 грн`, но не для распознанной ошибочной typed-формулы.

Правило:

```ts
if (r.qtyDiagnostic) {
  declaredHere = null
  checkBase = null
  totalStatus = "error"
} else if (typedCurrencyResult) {
  // typed total
} else {
  // старый literal total
}
```

### P0.4. Унарный минус молча теряется

Текущие места:

```text
PRIMARY_START_RE
primary()
parseQuantityExpression()
```

Предпочтительное исправление — добавить typed unary:

```text
unary := ("+" | "-")* primary
```

Кандидат должен включать знак, если он находится в начале выражения или после `(` / оператора. Минимальный безопасный вариант до реализации unary — отклонять найденный кандидат, если непосредственно перед `start` стоит унарный `-`.

Обязательный тест:

```text
-5 грн + 10 грн = → 5,00 грн
```

## 6. P1 — расхождения с заявленной грамматикой

### P1.1. Валютная typed-формула не увеличивает positions

Сейчас `positions` повторно считается старыми `RE.posPrice/RE.posCalc`, которые не знают о единице перед оператором. В результате:

```text
3720 грн - 10% =
```

даёт `total = 3348`, но `positions = 0`.

В BitrixUI итоговый блок скрывается условием `stats.positions > 0`.

Исправление:

```ts
type InlineResult = {
  html: string
  sum: number
  positions: number
  terminalQuantity: CalcValue | null
  qtyDiagnostic: ...
}
```

- обычная counted price: `positions += 1`;
- старый counted calc: `positions += 1`;
- числовая переменная-цена: `positions += 1`;
- успешная body quantity formula с currency: `positions += 1`;
- `context: total`, `грн/шт`, quote и невалютная величина: не увеличивают positions.

После этого удалить финальный повторный проход по `RE.pos*`.

### P1.2. Единица фактически ограничена одним словом

`tryReadUnit()` использует `^[^\s]+`, хотя план обещает несколько слов.

Необходим scanner, который читает unit до одного из разделителей:

- ` <operator> `;
- `)`;
- `=`;
- конец выражения.

Примеры:

```text
5 погонных метров + 5 погонных метров = → 10 погонных метров
10 кв. м + 5 кв. м =                    → 15 кв. м
100 листов А3 + 50 листов А3 =          → 150 листов А3
```

### P1.3. Формула только из переменных не запускается

Удалить раннюю проверку `if (!/\d/.test(candidate)) return null`. Кандидат допустим, если содержит хотя бы `number` или `[variable]`.

Обязательный тест:

```text
[a] = 50
[b] = 25
[a] шт + [b] шт = → 75 шт
```

### P1.4. Скобки поглощаются единицей

Unit scanner не должен включать `(`, `)` и `=`. Сейчас `шт)` становится отдельной единицей, а `(50 шт + 50 шт) / 2 =` ошибочно сообщает mismatch.

Обязательные тесты:

```text
(50 шт + 50 шт) / 2 = → 50 шт
50 шт * (2 + 1) =     → 150 шт
```

Процент от parenthesized quantity необходимо либо определить отдельно, либо отклонить. Нельзя превращать `(50 шт)%` в unit `шт)%`.

### P1.5. Нормализация `м2`/`м²` противоречит документации

`NFKC` превращает `²` в `2`, поэтому сейчас эти единицы совместимы. Для полиграфии это полезное поведение. Рекомендация:

- оставить `NFKC`;
- явно задокументировать `м2 == м²`, `м3 == м³`;
- не обещать строгое посимвольное равенство unitKey.

### P1.6. `грн.` не распознаётся как configured currency

Добавить отдельную нормализацию только для проверки currency:

```ts
normalizeCurrencyUnit(unit)
  = normalizeUnitKey(unit).replace(/\.$/, "")
```

Общую unit-нормализацию менять не нужно: завершающая точка может быть значимой для пользовательской единицы.

### P1.7. Сообщение mismatch всегда говорит «сложить»

`50 шт - 2 кг =` сейчас получает сообщение «Нельзя сложить». Передавать `op` в `QuantityCalcError.info` и выбирать «сложить/вычесть» в диагностике.

## 7. P2 — поведение и документация

### Клиентский знак равенства

План показывает клиентский результат как `= 3 348,00 грн`, но реализация отдаёт только значение. Нужно либо добавить `calc-eq` в export/client branch, либо изменить документацию. Рекомендация — вернуть `=`, поскольку он отделяет вычисленный итог от текстового префикса.

### Ручной результат после `=`

Source должен содержать:

```text
Итого: 3720 грн - 10% =
```

а не:

```text
Итого: 3720 грн - 10% = 3348 грн
```

Результат является проекцией рендера, а не частью источника. Иначе пользователь видит вычисленный и вручную введённый результат одновременно. Добавить это правило в обе подсказки и, при необходимости, diagnostic `quantity_manual_result`.

### Одна typed-формула на строку

Текущая реализация фактически обрабатывает последнее выражение перед последним `=`. Для поля ТЗ рекомендуется официально закрепить одну typed-формулу на строку. Это устраняет конфликт с `==highlight==` и не требует массива placeholders.

### Скрытый блок

При повторном рендере содержимого закрытого `/* ... */` quantity diagnostic получает строку открытия блока, а не реальную строку формулы. Нужно передавать фактический line index либо кешировать результат первого прохода скрытых строк.

## 8. Постоянные RU/UK-алиасы подытога

Начиная с версии синтаксиса `1.2.1`, движки должны одновременно принимать:

```text
Итого: 1500 грн
Разом: 1500 грн
```

Это не должно зависеть от выбранного языка интерфейса. `LOCALE.total` остаётся третьим настраиваемым/английским вариантом, поэтому при EN-настройке одновременно работают:

```text
Total:
Итого:
Разом:
```

Рендер сохраняет именно введённое слово. Свертки и служебные подписи могут использовать текущий `LOCALE.total`.

Реализация находится в `buildPatterns()` обоих движков через безопасное regex-alternation и покрыта общей fixture с `Итого` и `Разом` в одном документе.

## 9. Оптимизация без перегрузки парсера

### Оставить отдельный quantity module

Не объединять `quantity-calc` со старым `calc()` и не переносить его обратно в основной parser. Математическое ядро должно оставаться без HTML, CSS, `deal.amount` и режимов экспорта.

### Один анализ строки вместо повторов

Сейчас typed-выражение может разбираться:

1. в `looksLikeFormulaNotLabel()`;
2. повторно в `inline()`;
3. ещё раз в `renderSourceLines()`.

Ввести:

```ts
type LineAnalysis = {
  quantity: QuantityCalcResult | null
  isFormula: boolean
  isNumberedLabel: boolean
}
```

`render()` анализирует строку один раз и передаёт результат в `inline(text, { quantity })`. Редактор остаётся отдельной проекцией, но использует тот же pure result.

### Не строить полный AST документа

Для текущей задачи достаточно typed AST/результата одной формулы. Полный AST всего ТЗ не окупится в поле карточки сделки.

### Убрать повторный подсчёт stats по сырому тексту

`sum` и `positions` должны накапливаться из `InlineResult` в том же проходе, которым создаются blocks. Это одновременно быстрее и семантически надёжнее повторных regex.

### Оптимизировать поиск кандидата только после исправления корректности

Текущий перебор всех `PRIMARY_START_RE` потенциально квадратичный на искусственно длинной строке, но benchmark показывает около 1 мс на 9 КБ. Для реальных ТЗ это не проблема.

Если оптимизация всё же понадобится:

- один раз токенизировать кандидат;
- искать старт от завершающего `=` к ближайшей допустимой границе;
- не создавать `candidate.slice(start)` для каждого числа;
- сохранять первый error, но продолжать поиск более правого валидного выражения.

## 12. Рекомендуемая последовательность работ

### Коммит 1 — денежная корректность

1. `firstQuantity/checkBase`.
2. `grossTotal/effectiveTotal`.
3. запрет зелёного статуса при diagnostic.
4. Bitrix сравнивает effectiveTotal с deal.amount.
5. реальные fixtures со скидкой.

### Коммит 2 — защита от неверных вычислений

1. unary;
2. границы скобок;
3. variable-only expressions;
4. тесты неправильных/отрицательных выражений.

### Коммит 3 — обещанная произвольность единицы

1. multiword scanner;
2. currency punctuation;
3. NFKC contract;
4. сообщения операций.

### Коммит 4 — упрощение интеграции

1. positions из InlineResult;
2. удаление финального regex-rescan;
3. один analysis на строку;
4. source/client tests и документация.

RU/UK-алиасы `Итого`/`Разом` являются независимым безопасным патчем `1.2.1` и могут быть выпущены раньше этих четырёх этапов.

## 13. Критерии завершения

- сумма позиций до скидки и итог после скидки имеют разные явные поля;
- `deal.amount` сравнивается с итогом после корректировки;
- корректная скидка не показывает mismatch;
- ошибочная формула никогда не показывает зелёный `✓`;
- отрицательная величина не теряет знак;
- typed currency считается одной позицией;
- `Итого` и `Разом` распознаются одновременно при любой UI locale;
- несколько слов в единице работают согласно документации;
- выражения только с числовыми переменными вычисляются;
- скобки либо корректно поддерживаются, либо явно отклоняются;
- author/client/source дают согласованные проекции;
- все общие fixtures идентичны и проходят в обоих проектах;
- производительность 500 typed-строк не ухудшается относительно текущей более чем на 20%;
- старые формулы, plain prices, переменные, депозит, таблицы и dimension tokens проходят без изменений.
